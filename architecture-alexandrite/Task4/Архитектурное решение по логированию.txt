1. Анализ.
Логировать предлагается события:
- Shop API;
- CRM API;
- MES API;
- RabbitMQ;
- Базы данных;
- Аутентификации;

Список необходимых логов уровня INFO (события):
- Изменение статуса заказа: время, идентификатор покупателя, номер заказа;
- Изменение позиций в каталоге online магазина: время, идентификатор товара, статус;
- Изменение сущности Покупатель в CRM: время, идентификатор покупателя, статус;
- Изменение сущности Продавец в CRM: время, идентификатор продавца, статус;
- Операции с файлом 3D-модели: время, идентификатор файла, статус;
- Вход пользователя в систему: время, логин пользователя, идентификатор узла;
- Выход пользователя из системы: время, логин пользователя;

2. Мотивация.
2.1. Бизнес-метрики.
- Среднее время обработки заказа;
- Процент просроченных заказов;
- Частота отмен заказов;

2.2. Технические метрики.
- Среднее время расчёта стоимости;
- Время ответа API;
- Количество ошибок;

3. Предлагаемое решение.
3.1. Логирование предлагается реализовать при помощи следующих подходов.
 - Логирование приложений. Фреймворки для построения сервисов имеют встроенные инструменты логирования, которые позволяют разработчикам регистрировать сообщения разного уровня важности и распределять их по категориям;
 - Логирование с помощью агентов. Агенты или библиотеки, которые можно установить в системы или приложения для сбора логов;

Для сбора и хранения логов будет использоваться стек ELK - ElasticSearch, Logstash и Kibana, а также Filebeat для сбора логов непосредственно с узлов.

3.2. Политики безопасности.
- Доступ только из внутренней сети организации;
- Аутентификация, авторизация;
- Маскирование конфиденциальной информации, в том числе токенов;

3.2. Политики хранения.
- Определить срок хранения логов, не менее 14 дней;
- Отдельные индексы для разных сервисов;

4. Мероприятия.
Создание алертинга на основе логов для оперативного оповещения о сбоях и аномалиях: настройка правил в Kibana, отправка уведомлений (e-mail, sms, telegram).
