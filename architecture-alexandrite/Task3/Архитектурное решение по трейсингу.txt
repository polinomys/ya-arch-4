1. Анализ.
Целесообразно использовать трейсинг для поиска узких мест производительности, причин возникновения инцидентов, ошибок.

В частности, предлагается использовать трейсинг для отслеживания следующих взаимодействий:
- Internet Shop -> Shop API:  Потеря запроса от клиента, некорректная передача данных 3D-модели;
- CRM API -> Messages Queue: Потеря или дублирование сообщения;
- Messages Queue -> MES API: Потеря сообщения или отсутствие обработки;
- MES API -> MES: Долгая или неправильная обработка заказа оператором;
- MES API -> 3d files storage: Ошибки при расчёте стоимости — если нет файла или он повреждён;

2. Мотивация.
2.1. Технические метрики.
- Время обработки заказа от создания до отправки (end-to-end latency);
- Поиск "зависших" заказов (дольше обычного на определённом шаге);
- Быстрая диагностика и устранение ошибок (видно, на каком шаге упал процесс);
- Уменьшение случаев повторной отправки сообщений/заявок;

2.2. Бизнес-метрики.
- Снижение времени реакции на жалобы клиентов;
- Улучшение SLA с B2B-партнёрами (API-пользователями);
- Снижение потерь от потерянных заказов/контрактов;

3. Предлагаемое решение.
Выбранная технология:
- Использование OpenTelemetry + Jaeger;
- Сквозной трейсинг с использованием trace_id во всех API;

Необходимые доработки:
- Развёртывание Jaeger;
- Интеграция OpenTelemetry SDK: Shop API / CRM API / MES API;
- CI/CD: настроить логирование трейсов в окружениях.

4. Компромиссы.
- Невозможность доработки коробочных систем;
- Не большой горизонт хранения данных;
- Нагрузка на инфраструктуру;

5. Безопасность.
- Внедрение аутентификации и авторизации;
- Использование исключительно во внутреннем контуре организации;
- Журналирование событий при обращении с данными;

6. Схема.
